# StackVo Contracts — v1

This directory is the **agreement between the Bash CLI and the desktop app**. Both read the same
manifests, the same `.env`, and the same extension matrix. If either side changes what those mean
unilaterally, a project generated by one tool breaks under the other — which is the single failure
mode most likely to kill this port.

Nothing here is aspirational. Every rule was derived from source in the `stackvo` repo and verified
against the eight real projects on disk.

## Files

| File                  | What it fixes in place                                                                                                        |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `project.schema.json` | `projects/<name>/stackvo.json` — fields, defaults, runtime blocks, and the write/read rules JSON Schema can't express         |
| `env.schema.json`     | The 159 keys in `.env` — types, defaults, consumers, dead keys, the service catalog, and the completed dependency graph       |
| `php-extensions.json` | The 696-line Bash extension matrix as data: install method, apt packages, PECL versions per PHP release, compatibility floors |
| `ipc.json`            | The Tauri command + event surface, mapped 1:1 from the Express routes and Socket.io events                                    |
| `package.schema.json` | A service package's identity — `packages/<category>/<service>/package.json` in `stackvo-service-packages`                     |
| `package-version.schema.json` | One version of one service: image, ports, volumes, files, settings, connection, hashes. Replaces six compile-time tables |
| `registry.schema.json` | The signed index the app fetches before it can show a catalog                                                                |
| `compose-policy.json` | What a package's compose fragment may declare — an allowlist, read by the packages repo's CI and by the app after it renders  |
| `CONFLICTS.md`        | 18 conflicts found while writing the above, each with the decision v1 implements                                              |

## Running the checks

```bash
node tools/validate-contracts.mjs --root ../stackvo
node tools/validate-contracts.mjs --root ../stackvo --json   # machine-readable
```

Exits non-zero on any error. Seven suites: manifests, extension catalog, services, env keys, IPC
surface, reachability, package contracts.

The last one checks **this** repo rather than a checkout — the packages themselves live in
`stackvo/stackvo-service-packages`, which runs its manifests against these same three schema files.
What is checked here is the schemas: headers, a `required` name that is not among the properties, a
leaf nobody described, and the two files agreeing about which categories exist. That
`package-version.schema.json` and `pkg::Manifest` describe the same object is checked in
`src-tauri/tests/package_contract.rs`, because it needs the Rust type.

Current status against this machine's checkout: **4 errors, 28 warnings** — all four errors are
pre-existing StackVo bugs (C-06 ×3, C-09), not contract violations by the desktop app.

## The rules that matter

**Canonical spellings.** `runtime: "node"` (not `nodejs`), block key `node` (not `nodejs`), field
`server` (not `webserver`). Readers accept the legacy spellings; writers must never emit them.

**`runtime` absent means `php`.** All five pre-v1 PHP projects omit the key. Readers apply the default;
writers emit it explicitly.

**`php.extensions` must be the last key in the document**, one entry per line, at most 50 entries.
These constraints exist purely because the Bash parser extracts extensions with
`grep -A 50 '"extensions"'`. They are marked *temporary* and disappear with the Rust generator —
but while the Bash sidecar ships, violating them silently corrupts the generated Dockerfile.

**Errors instead of silent skips.** The Bash matrix answers "unknown extension" with an empty string,
so typos and incompatible extensions produce a container that builds fine and lacks the extension.
v1 makes these hard errors surfaced to the user. This is a deliberate behaviour change, recorded in
`php-extensions.json` → `resolution.errorPolicy`.

**PHP 8.0 is the floor.** `.env` advertises 5.6+, but the extension matrix assumes 8.0 throughout.

## Changing a contract

1. Change the contract file **first**, in its own commit.
2. Update `CONFLICTS.md` if the change resolves or creates a conflict.
3. Run the validator against a real checkout — it must stay at or below the current error count.
4. Only then change the Rust or Bash implementation.

Backwards-compatible additions (new optional field, new command) bump the minor version. Anything
that changes the meaning of an existing key, removes a field, or alters a default is **breaking** and
needs a migration path for the manifests already on disk — there is no "just regenerate", because
those files are user-authored source.

## Deliberately not decided here

- **Whether the Bash generator becomes a bundled sidecar or gets ported to Rust.** The contract is
  written so either choice works; that is the point. The manifests and `.env` mean the same thing
  regardless of which binary reads them.
- **Whether the containerised UI keeps shipping.** Settled: it does not. `STACKVO_UI_ENABLE` is
  recorded as dead — the desktop app is the only front end, and the skeleton ships no `core/ui`.
